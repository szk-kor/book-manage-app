# Book Management Application

## 概要
自分が所持している本や、これから読みたい本を管理するために作成したWebアプリケーションです。

Spring Bootの学習を進める中で、Controller・Service・Repositoryがどのように連携して動いているのかを理解することを目的に作成しました。

教材を参考にしつつ、そのまま写すのではなく、自分が実際に使うことを想定して検索機能やバリデーション、例外処理、テストなどを追加しています。

個人利用を前提としているため、現時点ではログイン・認証・認可機能は実装していません。

- 書籍一覧表示
- 書籍の新規登録
- 書籍情報の編集

- タイトル・著者によるキーワード検索
- 読書ステータスによる検索

## テスト
Repository、Service、Controllerの各層についてテストを実装しました。

### Repository
実際のDB操作を確認するため、検索・登録などのテストを作成しています。
Repositoryテストでは、通常利用しているH2のファイルDBとは別に、テスト専用のインメモリH2データベースを使用しています。

最初は通常利用しているDBに対してテストを実行していたため、既に登録していたデータが検索結果に含まれたり、アプリケーション起動中にDBファイルがロックされたりする問題がありました。
そのため、本番用とテスト用のDBを分離し、毎回同じ条件でテストできるようにしました。

また、テストデータのIDを手動で設定していた際、新規登録時の自動採番IDと競合して`DuplicateKeyException`が発生しました。
現在はテスト開始時にテーブルと自動採番を初期化し、IDを指定せずにテストデータを登録しています。

### Service
Mockitoを利用し、Repositoryの処理をモックした状態でServiceのテストを実装しました。

Repositoryそのものの動作ではなく、ServiceからRepositoryへ正しく処理を依頼できているかを確認しています。

### Controller
MockMvcとMockitoを利用し、以下のような処理をテストしています。

- 各画面へのアクセス
- 正常入力時のリダイレクト
- バリデーションエラー時の画面再表示
- 存在しないIDを指定した場合のエラー処理
- ステータス検索
- キーワード検索
- 不正なEnum値を送信した場合の400 Bad Request

Controllerテストを書く中で、Viewを返す処理とRedirectの違いについて理解を深めることができました。

また、参考教材では存在確認に`exists()`を使用していましたが、このアプリでは`searchById()`が`Optional<BookEntity>`を返す設計にしているため、`Optional.of()`と`Optional.empty()`を利用して存在・不存在をモックしています。

## 工夫した点・学んだこと
### Controllerにおける入力値のバリデーション
当初、画面から受け取った値をどこでバリデーションし、どのようにDB保存までつなげるのかが分かっていませんでした。

入力値を直接Entityで受け取るのではなく、`BookForm`で一度受け取り、バリデーションを実行する構成にしています。

エラーがある場合は入力画面を再表示し、問題がなければ`BookForm`の内容を`BookEntity`へ移してServiceへ渡します。

この実装を通して、

- `BookForm`は画面から入力された値を受け取る
- `BookEntity`はDB上のデータを表す
- `BindingResult`はバリデーション結果を受け取る
- 
という役割の違いを理解しました。

### テスト用DBの分離
最初は開発時に利用しているDBをそのままRepositoryテストでも使用していました。
その結果、登録済みデータによってテスト結果が変わるなど、テストが実行環境に依存する状態になっていました。

そこでテスト専用のインメモリDBを用意し、各テストを独立して実行できるようにしました。

テストでは「たまたま今のDBなら通る」状態ではなく、毎回同じ条件で再現できることが重要だと学びました。

### 自動採番と登録日時のテスト
新規登録テストでは、IDの自動採番と`LocalDateTime.now()`の扱いにも詰まりました。

IDを手動で指定したテストデータとDB側の自動採番が競合したため、自動採番の状態も含めて初期化するように変更しました。

また、`LocalDateTime.now()`は取得するたびに値が変わるため、Entity全体を完全一致で比較する方法は採用せず、タイトル・著者・ステータスが一致することを確認する形にしています。

すべての値を無理に比較するのではなく、「このテストでは何を確認したいのか」に応じて比較対象を決める必要があると学びました。

### DTOを導入しなかった理由
DTOの導入も検討しましたが、現状ではEntityと画面に表示するデータの差が小さく、DTOを追加することで変換処理が増える方が複雑になると判断しました。

機能を増やせばよいのではなく、現在の規模や用途に対して本当に必要かを考えて導入することも大切だと考えています。

### 例外処理
存在しない書籍IDが指定された場合は`BookNotFoundException`を発生させ、`@ControllerAdvice`を利用した共通の例外処理で`error.html`を表示するようにしています。

Controller内ですべてのエラー処理を書くのではなく、例外処理を別のクラスに分けることで役割を分離しました。
